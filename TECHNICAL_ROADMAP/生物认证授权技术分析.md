# 生物认证授权技术分析

# 生物认证授权技术构成

技术构成：生物认证编排层、安全元件SE（Secure Element）、可信执行环境TEE（Trusted Execution Environment）、可验证/审计层。

1. **生物认证编排层：**负责统一管理生物认证请求、系统 UI、认证流程、认证模态选择、失败回退与底层安全模块调用的系统级接口层。
    1. BiometricPrompt 是 Android 提供的系统级生物认证接口与交互框架，用于统一调用指纹、人脸、虹膜等认证方式，显示系统提供的可信认证 UI，并协调底层 TEE、Keystore、StrongBox 等安全模块完成认证。
2. **安全元件SE：**Secure Element，一个安全元件/安全芯片，重点是保护密钥、证书和设备身份，并在芯片内部完成安全存储密钥、执行签名/解密、做设备认证、抗物理篡改等密码操作。
3. **可信执行环境TEE：**Trusted Execution Environment，是主处理器中的一个隔离执行环境。它和普通操作系统/应用处理器分开，用来运行更敏感的代码，保护敏感数据和关键判定逻辑。其核心不是“存储”，而是在受保护边界内执行。
4. **系统日志/安全日志审计层：**操作系统或安全框架中的审计记录机制。对认证、授权、密钥使用与安全相关事件进行记录、存储与审查的系统级证据层，用于提供事件的时间顺序、上下文、结果状态与可追溯性。

# 主流生物认证授权链路

App → 系统级生物认证入口 → 系统认证编排框架 → TEE / Secure Enclave / StrongBox / SE → 密钥释放或授权结果输出 → 系统日志/安全日志审计层。

# 主流生物认证授权技术路线

### 第一类：一体化 SoC / Secure Enclave 路线

**代表厂商**

Apple，部分高端 Qualcomm 平台

**核心特征**

生物模板处理、存储、匹配、密钥使用与授权输出，尽可能在同一受保护安全域内完成，形成高度一体化的封闭安全边界。

**优点**

安全边界最集中，模板、匹配结果和密钥尽量不离开安全域；系统协同能力最强，传感器、SoC、安全子系统、操作系统、支付栈和开发接口可统一设计；因此在抗伪造、活体检测、可信 UI 和抗中间链路攻击方面通常最强。

**缺点**

体系封闭，可移植性差，离开特定生态难以复用；难以直接扩展为开放协议式的人类授权基础设施；输出通常是本机认证结果，而不是面向第三方独立验签的可验证授权断言。

### **第二类：Android OEM 的 TEE / StrongBox / eSE 组合路线**

**代表厂商**

Android OEM 厂商、Google Android 安全框架生态、采用 TEE / StrongBox / eSE 的终端厂商

**核心特征**

核心不是统一硬件，而是**统一认证框架、接口规范和安全分级**，强调“统一认证框架 + 不同硬件实现”。上层通常通过 BiometricPrompt 发起认证，下层由不同 OEM 结合 TEE、Keystore、StrongBox、eSE 及不同生物模组具体实现。

**优点**

灵活性高，适配不同厂商、不同价位和不同 SoC 平台；生态覆盖广，适合大规模部署；支持分层演进，高端设备可采用更强硬件安全模块，普通设备也可提供基本可信认证能力。

**缺点**

不同厂商、机型和代际之间安全能力差异较大，安全边界不统一；高端实现可接近一体化安全架构，低端实现往往只满足基础需求；更擅长系统内部可信认证，不擅长形成跨 OEM、跨平台、可独立审计的统一授权证明层。

### **第三类：分立式“传感器 + MCU + Secure Element”路线**

**代表厂商**

Microchip、NXP、ST，以及各类 IoT、工业控制、外设认证方案厂商

**核心特征**

传感器负责采集与初步判断，MCU 负责逻辑编排，Secure Element 负责根密钥、签名、设备身份、证书与安全计数；整体采用分立式架构实现认证与授权。

**优点**

开放性强、成本较低、易于快速原型化；可移植性强，更换 MCU、SE 或传感器后仍可保留总体架构；适合独立硬件授权器、工业终端、机器人外设和企业级安全外设，也更适合扩展为跨设备、跨平台的人类授权协议层。

**缺点**

安全边界相对分散，传感器、MCU 与 SE 往往不在同一可信边界内；系统安全高度依赖工程实现质量，包括总线保护、secure boot、challenge 绑定、防篡改日志和异常状态处理；上限较高，但要达到 Apple 式一体化方案的安全性与体验，难度很大。

# 生物认证授权技术构成比较

| 对比维度 | 分立式 HumanLink 路线 | Apple / Secure Enclave 路线 | Android OEM / TEE + StrongBox 路线 | 工业 / IoT Secure Element 路线 |
| --- | --- | --- | --- | --- |
| 典型架构 | 生物模块 + MCU + Secure Element + SDK + Assertion | 传感器 + SoC + Secure Enclave + OS | BiometricPrompt + TEE / Keystore + StrongBox / eSE | 传感器 / MCU + Secure Element + 设备证书 |
| 认证入口 | 自定义 SDK、AI Gateway / approval hook、Challenge 流程 | Touch ID / Face ID API 与系统 UI | BiometricPrompt 与系统认证框架 | 通常为厂商自定义接口 |
| 生物处理位置 | 本地指纹模块完成采集与匹配，匹配结果交由 MCU / SE 绑定签名 | 模板处理、存储、匹配尽量在 Secure Enclave 内完成 | 取决于 OEM，可在 TEE、StrongBox 或独立生物模组中完成 | 多数不负责复杂生物匹配，偏设备认证 |
| MCU / 控制逻辑 | ESP32 负责流程编排、Challenge 处理、传感器与 SE 调度 | 由 SoC / 系统安全子系统统一编排 | 由 Android 系统框架、TEE、OEM 安全组件协同 | MCU 负责设备逻辑和 SE 调度 |
| Secure Element / 私钥保护 | ATECC608A 负责私钥存储、ECDSA 签名、设备身份 | Secure Enclave 承担密钥保护与安全运算 | StrongBox / eSE / TEE 负责高等级密钥保护 | SE 是核心组件，负责设备身份、证书、签名 |
| 授权输出 | `HumanPresenceAssertion`：绑定操作、设备、Challenge 与签名 | 本机认证结果或系统授权结果 | 系统认证状态、Keystore / StrongBox 授权结果 | 设备签名、证书、认证日志 |
| 审计 / 状态层 | Verifier + Registry / Revocation / Audit log | 主要为系统内部日志 | 主要为系统内部安全日志 | 可有设备日志或证书状态，但通常不面向人类授权 |

# 生物认证授权技术特点比较

| 对比维度 | 分立式 HumanLink 路线 | Apple / Secure Enclave 路线 | Android OEM / TEE + StrongBox 路线 | 工业 / IoT Secure Element 路线 |
| --- | --- | --- | --- | --- |
| 核心目标 | AI 高风险操作的人类在场授权证明 | 本机解锁、支付、系统身份认证 | App 调用系统认证能力 | 设备身份、通信安全、工业认证 |
| 授权对象 | 具体操作参数，如转账、删文件、发命令 | 设备解锁、支付或系统授权 | App 会话或系统认证请求 | 设备或局部业务逻辑 |
| 安全边界 | 分散，需依赖 secure boot、链路保护、SE 签名和模块 attestation 补强 | 最集中，模板、匹配、密钥尽量在同一安全域 | 中等到高，取决于 OEM 实现质量 | 中等，SE 强但生物处理通常在外部 |
| 操作绑定能力 | 强，`actionHash` 与操作摘要、Challenge、设备 DID 绑定 | 中等，支付确认较强，但不开放为通用操作断言 | 弱到中等，主要绑定系统认证请求 | 中等，取决于业务实现 |
| 第三方验证与举证 | 强目标：可独立验签、查设备状态、查撤销状态、生成审计证据 | 弱，主要依赖本机或 Apple 生态 | 弱到中等，依赖系统 API 和 OEM 实现 | 中等，可验证设备签名，但不一定验证人类授权 |
| 开放性与可移植性 | 高，可替换传感器、MCU、SE，并通过 HAI 接入不同 Agent / 企业平台 | 低，强绑定 Apple 硬件和系统生态 | 中等，Android 生态内兼容较强，但 OEM 差异大 | 高，适合嵌入不同硬件平台 |
| Agent 场景适配 | 强，可拦截高风险 Agent 行为并生成授权证明 | 弱，不是为 Agent 授权设计 | 弱到中等，可辅助登录但难绑定具体操作 | 中等，更适合设备认证 |
| 主要优势 | 跨平台、可举证、可审计、适合 Agent 高风险操作 | 安全边界最强、用户体验最好 | 生态覆盖广、系统接口成熟 | 成本低、硬件灵活、易嵌入 |
| 主要短板 | 当前 demo 活体检测、模块 attestation、链路安全仍需增强 | 封闭，难形成开放授权协议 | OEM 差异大，外部证明能力弱 | 缺少统一人类授权证明层 |
| 与HumanLink 的差异 | 将“真人在场”转化为可验证 Assertion，并绑定具体操作与审计链路 | 主要强在本机安全，不输出开放授权断言 | 主要强在系统认证框架，不形成跨平台授权证据 | 主要强在设备身份，不完整表达“人类对具体操作授权” |
