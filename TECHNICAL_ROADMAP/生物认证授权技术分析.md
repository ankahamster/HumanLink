# 生物认证授权技术分析

## 目的

这份文档整理了主流生物认证授权技术路线，并结合 `HumanLink` 当前的分立式硬件方案，明确其优势、短板和后续增强方向。

---

## 技术构成

生物认证授权系统通常由四层组成：

1. **生物认证编排层**
   - 负责统一管理认证请求、系统 UI、认证流程、失败回退和底层安全模块调用。
   - 典型例子是 Android 的 `BiometricPrompt`。
2. **安全元件 SE**
   - 负责保护密钥、证书和设备身份。
   - 在芯片内部完成签名、解密、设备认证等密码学操作。
3. **可信执行环境 TEE**
   - 是主处理器上的隔离执行环境。
   - 用于运行敏感逻辑，保护关键判定过程和敏感数据。
4. **审计层**
   - 记录认证、授权、密钥使用和安全事件。
   - 形成时间顺序、上下文和结果状态可追溯的证据层。

---

## 主流授权链路

```text
App
  -> 系统级生物认证入口
  -> 系统认证编排框架
  -> TEE / Secure Enclave / StrongBox / SE
  -> 密钥释放或授权结果输出
  -> 系统日志 / 安全日志审计层
```

---

## 三类主流技术路线

### 1. 一体化 SoC / Secure Enclave 路线

代表：

- Apple
- 部分高端 Qualcomm 平台

特点：

- 生物模板处理、匹配、密钥使用和授权输出尽可能在同一安全域中完成
- 安全边界最集中，系统协同能力最强

优点：

- 模板、匹配结果和密钥尽量不离开安全域
- 用户体验和可信 UI 通常最好
- 抗中间链路攻击、抗篡改能力通常最强

局限：

- 体系封闭，可移植性差
- 更像本机可信认证，不是开放的人类授权证明协议
- 难直接扩展成面向第三方独立验签的授权断言层

### 2. Android OEM 的 TEE / StrongBox / eSE 组合路线

代表：

- Google Android 安全框架生态
- 各类 Android OEM 厂商

特点：

- 统一认证框架，上层通过 `BiometricPrompt` 发起
- 下层由不同 OEM 结合 TEE、Keystore、StrongBox、eSE 与生物模组具体实现

优点：

- 灵活性高，覆盖面广
- 易于在不同设备和价位段部署
- 高端实现安全能力较强

局限：

- OEM 之间能力差异大
- 安全边界不统一
- 更适合系统内部认证，不适合形成跨厂商、跨平台的统一授权证明

### 3. 分立式“传感器 + MCU + Secure Element”路线

代表：

- Microchip
- NXP
- ST
- IoT / 工业控制 / 安全外设方案

特点：

- 传感器负责采集与初步判断
- MCU 负责编排逻辑
- SE 负责根密钥、设备身份、签名与证书

优点：

- 开放性强
- 成本较低，适合快速原型
- 适合独立硬件授权器、机器人外设、企业级安全外设
- 更适合演进为跨设备、跨平台的人类授权协议层

局限：

- 安全边界分散
- 对 secure boot、链路保护、防重放、审计设计要求高
- 要达到封闭一体化方案的体验和安全上限，工程难度很大

## HumanLink 当前路线定位

`HumanLink` 当前采用的是第三类路线，即：

```text
指纹模块 + MCU + Secure Element + SDK + Assertion
```

当前参考实现：

- 指纹模块：`JM-101`
- MCU：`ESP32`
- 安全芯片：`ATECC608A`

其核心优势不在于“复制 Apple 式封闭安全边界”，而在于：

- 面向 Agent 高风险操作
- 强调跨平台接入
- 强调 `actionHash` 绑定
- 强调 Assertion 可独立验签
- 强调审计与争议举证能力

## 技术对比结论

### HumanLink 相对封闭系统的差异

- 封闭系统更强在本机认证和一体化体验
- HumanLink 更强在开放接入、跨平台适配和对具体操作的授权绑定

### HumanLink 相对工业 IoT 方案的差异

- 工业 IoT 方案更偏设备身份和通信安全
- HumanLink 关注的是“真人是否对某个具体高风险操作进行了授权”

## 工程增强重点

从当前 demo 走向更强安全形态，建议重点补强以下几类能力：

### 1. ESP32 自身可信

当前：

- `ESP32` 负责接收挑战、调度指纹模块和 `ATECC608A`

建议增强：

- `Secure Boot`
- `Flash Encryption`
- `Anti-rollback`

目标：

- 防止恶意固件绕过指纹/活体流程并直接调用安全芯片签名

### 2. 外设模块可信

当前：

- `JM-101` 负责采集和本地模板匹配

建议增强：

- 引入带模块证书的生物认证模组
- 引入具备签名输出能力的活体模块
- 或在模块侧增加独立 `Secure Element`

目标：

- 防止认证外设被替换
- 提升模块级 attestation 能力

### 3. 模块链路可信

当前链路：

- 指纹模块与 `ESP32` 间通过串口
- `ESP32` 与 `ATECC608A` 间通过 `I2C`
- 主机与设备间通过 `USB Serial`

建议增强：

- 为关键通信加入 `nonce`
- 加入 `counter`
- 加入 `MAC` 或加密通道

目标：

- 防监听
- 防重放
- 防注入
- 防模块替换

### 4. 用户确认可信

当前：

- `display` 内容由验证方填写，再由设备侧授权

建议增强：

- 增加设备端可信显示
- 增加按钮确认或短 hash 校验

目标：

- 让用户看到的操作摘要与最终签名绑定的 `actionHash` 保持一致

### 5. 活体能力可信

当前：

- `JM-101` 更接近指纹匹配触发，不是强活体检测模组

建议增强：

- 升级到具备本地活体判断、防伪造、模块证书、签名输出和安全密钥存储能力的模组

## 对 HumanLinkPay 的直接意义

这些分析直接影响 `HumanLinkPay` 这类 Agent 支付场景：

- 高风险支付不应只停留在“软件确认”
- 授权必须绑定具体支付参数，而不是绑定抽象会话
- 审计记录应同时覆盖 SDK、Gateway 和链上执行层
- 后续若要走向更高等级安全，需要补强活体、设备 attestation 和链路保护

---

## 总结

`HumanLink` 当前最合理的技术路线，不是去复制封闭生态，而是：

- 用开放的分立式架构实现参考硬件
- 用统一 Assertion 语义定义授权证明
- 用可验证、可审计、可扩展的协议层服务 Agent 高风险操作

这条路线的核心价值是：

**把“真人在场授权”转化成可以独立验签、绑定具体操作、可跨平台接入的授权证明。**
