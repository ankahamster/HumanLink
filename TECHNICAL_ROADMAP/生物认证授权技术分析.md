# 生物认证授权技术分析

# 生物认证授权技术构成

技术构成：生物认证编排层、安全元件SE（Secure Element）、可信执行环境TEE（Trusted Execution Environment）、可验证/审计层。

1. \*\*生物认证编排层：\*\*负责统一管理生物认证请求、系统 UI、认证流程、认证模态选择、失败回退与底层安全模块调用的系统级接口层。
   1. BiometricPrompt 是 Android 提供的系统级生物认证接口与交互框架，用于统一调用指纹、人脸、虹膜等认证方式，显示系统提供的可信认证 UI，并协调底层 TEE、Keystore、StrongBox 等安全模块完成认证。
2. \*\*安全元件SE：\*\*Secure Element，一个安全元件/安全芯片，重点是保护密钥、证书和设备身份，并在芯片内部完成安全存储密钥、执行签名/解密、做设备认证、抗物理篡改等密码操作。
3. \*\*可信执行环境TEE：\*\*Trusted Execution Environment，是主处理器中的一个隔离执行环境。它和普通操作系统/应用处理器分开，用来运行更敏感的代码，保护敏感数据和关键判定逻辑。其核心不是“存储”，而是在受保护边界内执行。
4. \*\*系统日志/安全日志审计层：\*\*操作系统或安全框架中的审计记录机制。对认证、授权、密钥使用与安全相关事件进行记录、存储与审查的系统级证据层，用于提供事件的时间顺序、上下文、结果状态与可追溯性。

# 主流生物认证授权链路

App → 系统级生物认证入口 → 系统认证编排框架 → TEE / Secure Enclave / StrongBox / SE → 密钥释放或授权结果输出 → 系统日志/安全日志审计层。

# 主流生物认证授权技术路线

生物认证授权技术路线不宜只按厂商或生态划分，更严谨的分类方式应基于以下技术问题：

| 分类依据 | 核心问题 |
|---|---|
| 可信边界 | 生物模板、匹配逻辑、私钥和授权判断位于同一安全域，还是分布在多个模块中 |
| 编排主体 | 是 SoC / 系统安全子系统、OS 认证框架、MCU，还是外部认证器协议 |
| 私钥保护位置 | 私钥位于 Secure Enclave、TEE / StrongBox / Keystore / eSE、独立 SE，还是硬件认证器内部 |
| 授权输出 | 输出本机认证结果、系统密钥授权结果、设备签名，还是可第三方验签的授权断言 |
| 授权对象 | 授权对象是登录 / 解锁 / App 会话 / 凭证访问，还是具体操作的 actionHash |
| 开放性 | 是否可跨平台、跨设备、跨 Agent / Gateway / 企业系统独立验证和审计 |

## 技术路线总览

| 技术路线 | 可信边界 | 谁负责编排 | 私钥在哪里 | 输出什么 | 开放性 | 最适合场景 |
|---|---|---|---|---|---|---|
| 一体化安全域架构 | 单一强安全域 | SoC / 系统安全子系统 | Secure Enclave / 安全域 | 本机认证结果 / 系统授权 | 低 | 本机解锁、支付、系统身份认证 |
| 平台编排型 TEE / StrongBox 架构 | OS + TEE / StrongBox / eSE | 系统认证框架 | TEE / StrongBox / Keystore / eSE | 系统认证状态 / 密钥授权结果 | 中 | App 认证、系统级生物认证、移动端 MFA |
| 分立式认证器 + SE 架构 | 传感器、MCU、SE 分离 | MCU | 独立 Secure Element | 可设计为 HumanPresenceAssertion | 高 | 独立授权器、Agent 高风险动作授权、IoT / 企业外设 |
| 硬件认证器 / 设备认证架构 | 独立硬件认证器 | Client / RP + Authenticator | 认证器内部 | WebAuthn assertion / 设备签名 | 高 | 登录认证、FIDO2、设备认证、抗钓鱼 |

## 四类路线的核心特征

| 技术路线 | 核心特征 | 主要优势 | 主要短板 |
|---|---|---|---|
| 一体化安全域架构 | 生物模板处理、模板存储、匹配逻辑、密钥使用和授权输出尽量位于同一受保护安全域内 | 安全边界最集中；链路短；用户体验好；抗中间链路攻击能力强 | 封闭；可移植性差；通常不输出开放、第三方可验签的授权断言 |
| 平台编排型 TEE / StrongBox 架构 | 上层由系统认证框架统一编排，下层由 TEE、StrongBox、Keystore、eSE 或 OEM 生物模组实现 | 接口统一；生态覆盖广；适合大规模移动端部署；高端设备可获得较强安全性 | OEM 差异大；安全等级不均一；外部证明能力弱；主要服务 App / 系统认证 |
| 分立式认证器 + SE 架构 | 传感器或活体模块负责采集与初步判断，MCU 负责编排，SE 负责不可导出私钥、设备身份和签名 | 开放性强；模块可替换；成本较低；适合独立硬件授权器和跨平台授权协议 | 安全边界分散；需要补强 secure boot、模块 attestation、总线保护、防重放和异常处理 |
| 硬件认证器 / 设备认证架构 | 独立硬件认证器持有不可导出私钥，对 challenge 签名，证明设备持有和用户在场 | 标准成熟；抗钓鱼；企业部署广；第三方 RP 可验证签名 | 默认语义是登录认证或设备认证，不天然表达具体操作的人类授权 |

# 生物认证授权技术构成比较

| 对比维度 | 一体化安全域架构 | 平台编排型 TEE / StrongBox 架构 | 分立式认证器 + SE 架构 | 硬件认证器 / 设备认证架构 |
|---|---|---|---|---|
| 典型形态 | 传感器 + SoC + Secure Enclave / 安全子系统 + OS | BiometricPrompt / 系统认证框架 + TEE / Keystore / StrongBox / eSE | 生物模块 + MCU + Secure Element + SDK + Assertion | YubiKey、FIDO2 security key、PIV smart card、工业 SE 认证设备 |
| 认证入口 | 系统级生物认证 API 与可信 UI | App 调用系统生物认证接口，由系统框架编排 | 自定义 SDK、AI Gateway、approval hook、Challenge 流程 | Client / Browser / RP 发起 challenge-response |
| 生物处理位置 | 模板处理、存储、匹配尽量在安全域内完成 | 取决于 OEM，可在 TEE、StrongBox、eSE 或独立生物模组中完成 | 本地生物模块完成采集与匹配，结果交由 MCU / SE 绑定签名 | 通常不做复杂生物处理，或只做 user presence / user verification |
| 控制逻辑 | SoC / 系统安全子系统统一编排 | OS 认证框架、TEE、Keystore、OEM 安全组件协同 | MCU 负责 Challenge 处理、模块调度、结果组装和错误路径 | Client / RP 与 Authenticator 按协议交互 |
| 私钥保护 | Secure Enclave / 硬件安全域 | TEE / StrongBox / Keystore / eSE | 独立 Secure Element，例如 ATECC608A | 认证器内部安全芯片 |
| 授权输出 | 本机认证结果或系统授权结果 | 系统认证状态、Keystore / StrongBox 授权结果 | 可设计为 HumanPresenceAssertion，绑定操作、设备、Challenge 与签名 | WebAuthn assertion、设备签名、证书、认证日志 |
| 审计 / 状态层 | 主要为系统内部日志 | 主要为系统内部安全日志或平台日志 | Verifier + Registry / Revocation / Audit log | RP 认证记录、设备证书状态、认证日志 |
| 第三方验证能力 | 弱，主要依赖本机或生态 API | 弱到中等，依赖系统 API 和 OEM 实现 | 强目标，可独立验签、查设备状态、查撤销状态 | 中到强，但主要验证设备认证 / 登录，不一定验证人类对具体动作授权 |

# 生物认证授权技术特点比较

| 对比维度 | 一体化安全域架构 | 平台编排型 TEE / StrongBox 架构 | 分立式认证器 + SE 架构 | 硬件认证器 / 设备认证架构 |
|---|---|---|---|---|
| 核心目标 | 本机解锁、支付、系统身份认证 | App 调用系统生物认证能力 | 独立硬件授权、跨平台认证、具体操作授权 | 登录认证、设备认证、抗钓鱼 |
| 授权对象 | 设备解锁、支付或系统授权 | App 会话、系统认证请求、密钥使用请求 | 具体操作参数，如转账、删文件、发命令、Agent 工具调用 | 登录 challenge、RP challenge、设备认证 challenge |
| 安全边界 | 最集中，模板、匹配、密钥尽量在同一安全域 | 中等到高，取决于 OEM 和硬件等级 | 分散，依赖 secure boot、链路保护、模块 attestation 和 SE 签名补强 | 独立认证器边界，主机通常不持有私钥 |
| 操作绑定能力 | 中等，支付确认较强，但通常不开放为通用操作断言 | 弱到中等，主要绑定系统认证请求或密钥使用请求 | 强，可绑定 actionHash、Challenge、设备 DID、模块状态和审计记录 | 中等，可绑定 challenge，但默认语义多为登录或认证 |
| 第三方验证与举证 | 弱，主要依赖本机系统或封闭生态 | 弱到中等，依赖平台 API、OEM 安全实现和系统日志 | 强目标：可独立验签、查设备状态、查撤销状态、生成审计证据 | 中到强，RP 可验证签名，但不一定表达具体人类授权 |
| 开放性与可移植性 | 低，强绑定硬件和系统生态 | 中等，生态内兼容较强，但 OEM 差异大 | 高，可替换传感器、MCU、SE，并接入不同 Agent / Gateway / 企业平台 | 高，FIDO / WebAuthn 等标准成熟，跨平台部署广 |
| Agent 场景适配 | 弱，不是为 Agent 授权设计 | 弱到中等，可辅助登录或敏感操作认证，但难绑定具体 Agent action | 强，可拦截 Agent 高风险行为并生成授权证明 | 中等，可做强认证，但默认不表达 Agent actionHash 授权 |
| 主要优势 | 安全边界强、体验好、系统协同能力强 | 接口统一、生态覆盖广、适合移动端大规模部署 | 开放、可组合、可审计、适合 AI 高风险动作授权 | 标准成熟、抗钓鱼、硬件私钥保护成熟 |
| 主要短板 | 封闭，难形成开放授权协议 | OEM 差异大，外部证明能力弱 | 工程复杂，需要补强模块可信、链路安全和固件可信 | 主要强在认证，不完整表达“人类对具体操作授权” |
