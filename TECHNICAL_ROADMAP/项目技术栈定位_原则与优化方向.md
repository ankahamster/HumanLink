# 项目技术栈定位、原则与优化方向

## 文档目的

这份文档用于明确 `HumanLink` 的技术栈定位，不把项目理解为单一硬件安全产品，而是把它定位为：

**面向 AI 高风险操作的人类在场授权证明协议层。**

---

## 技术栈核心定位

`HumanLink` 的重点不是构建一个封闭的单一硬件系统，而是设计开放协议层，定义面向 AI 高风险操作的**人类在场授权证明**。

工程路线是：

- 通过开放接口、模块化硬件和统一验证协议
- 实现可验证、可审计、可扩展的人类授权基础设施

---

## 三个核心原则

### 1. 协议优先，硬件作为可信执行载体

`HumanLink` 首先是协议层，而不是单一硬件产品。

协议层负责定义：

- `Challenge`
- `actionHash`
- `HumanPresenceAssertion`
- 设备身份
- 签名格式
- 验证流程
- 审计接口

硬件负责：

- 执行人类在场验证
- 保护不可导出私钥
- 对与具体操作绑定的上下文进行签名

### 2. 开放接入，基于分立式硬件架构的 HAI 抽象接口

当前参考实现：

- `ESP32 + JM-101 + ATECC608A`

但 `HAI` 不应绑定具体硬件型号，而应定义“合规 HumanLink Issuer 必须具备的能力与输出格式”。

开放性应体现在四个方面：

- **硬件开放**
  - 传感器、MCU、SE 可以升级或替换
  - 但 Assertion 的数据结构、签名语义和验证逻辑应保持兼容
- **接入开放**
  - Agent harness、AI Gateway、企业平台、本地应用都可以通过统一 SDK 接入
- **验证开放**
  - 不同 Verifier 都可以基于公开格式和验证流程独立验签
- **审计开放**
  - 不同审计系统都可以检查授权记录、设备状态、撤销状态和操作绑定关系

### 3. 安全原则参考封闭硬件系统，但工程路线不依赖封闭生态

封闭系统通常在安全边界和一体化能力上更强，但 `HumanLink` 不需要复制其闭环生态。

更重要的是借鉴它们的关键安全机制：

- 硬件根信任
- 私钥不可导出
- 用户确认内容与最终签名执行内容一致
- 上下文绑定签名
- 防重放

---

## 为什么这种定位适合 HumanLink

相对于传统“软件审批”或“钱包内审批”，`HumanLink` 追求的是：

- 把高风险操作的人类授权变成独立的密码学证据
- 让授权对象绑定具体操作，而不是泛化到整个会话
- 让第三方可以独立验证，而不依赖平台自己解释

这也是它在 Agent 场景里的独特价值：

- Agent 可以理解任务
- Gateway 可以执行策略
- HumanLink 提供“这个动作真的获得了真人在场授权”的证明

## 当前参考技术栈

### 硬件侧

- `ESP32`
- `JM-101` 指纹模块
- `ATECC608A Secure Element`

### 软件侧

- `HumanLink SDK`
- Gateway / Verifier / Registry / Revocation / Audit 逻辑
- 面向 Agent 的接入层

### 协议侧

- `Challenge`
- `actionHash`
- `HumanPresenceAssertion`
- 设备身份与签名校验
- 审计记录

---

## 技术栈不是“堆功能”，而是分层

建议始终按下面四层来理解项目：

### 1. 授权协议层

负责定义：

- 授权对象是什么
- Assertion 长什么样
- 如何验证
- 如何审计

### 2. 硬件执行层

负责：

- 生物认证
- 不可导出私钥保护
- 对授权上下文签名

### 3. 验证与审计层

负责：

- 验证签名
- 检查设备状态
- 检查撤销状态
- 形成争议举证材料

### 4. 接入与应用层

负责：

- AI Agent
- Gateway
- 企业系统
- 本地应用

这层不应重写授权逻辑，而应调用统一的 HumanLink 授权能力。

## 硬件架构优化方向

### 1. ESP32 自身可信

当前基础：

- `ESP32` 接收 `H_doc`
- 调度 `JM-101` 与 `ATECC608A`
- 返回硬件签名

待增强：

- `Secure Boot`
- `Flash Encryption`
- `Anti-rollback`

目标：

- 防止恶意固件绕过认证流程直接触发签名

### 2. 外设模块可信

当前基础：

- `JM-101` 完成指纹采集和本地模板匹配
- Assertion 层已有 `score` 与 `sensor_serial`

待增强：

- 模块级公私钥
- 模块证书
- 强 attestation
- 更强活体判断能力

目标：

- 防止认证模块被替换

### 3. 模块链路可信

当前链路：

- `JM-101 <-> ESP32`：串口
- `ESP32 <-> ATECC608A`：`I2C`
- 主机 <-> 设备：`USB Serial`

待增强：

- `nonce`
- `counter`
- `MAC`
- 加密通道

目标：

- 防监听
- 防重放
- 防注入
- 防链路层替换

### 4. 授权证据与审计可信

当前基础：

- 已设计 `HumanPresenceAssertion`
- 包含 `challenge`、`actionHash`、`requiredIssuerDID`、`nonce`、`origin`
- `proof` 字段包含 `ECDSA` 签名

待增强：

- 把模块证书纳入证据
- 把活体结果签名纳入证据
- 把 ESP32 固件状态纳入证据
- 把设备端确认状态纳入证据

目标：

- 让 Verifier 能同时检查设备、模块、固件与 Assertion 状态

### 5. 用户确认可信

当前基础：

- `display` 内容由验证方填写，再交由设备确认

待增强：

- 设备端可信显示
- 物理按键确认
- 短 hash 校验

目标：

- 保证用户看到的摘要与最终签名绑定的 `actionHash` 一致

### 6. 活体能力可信

当前基础：

- `JM-101` 更偏指纹匹配，不是强活体检测模组

待增强：

- 升级到具备本地活体判断、防伪造、模块证书和签名输出能力的模组

## 对 Agent 场景的直接影响

这套定位直接决定了 `HumanLink` 在 AI Agent 体系里的角色：

- 它不是替代钱包
- 它不是替代策略引擎
- 它不是替代执行系统

它负责的是：

**为高风险操作提供“真人在场 + 具体操作绑定 + 可验证证据”的授权层。**

这意味着：

- Agent 不应直接拥有无限执行权
- Gateway 不应只依赖自然语言或 UI 状态
- 高风险动作需要落到 `actionHash`
- Assertion 需要能被独立验签和审计

---

## 对 HumanLinkPay 的意义

在 `HumanLinkPay` 这类 Agent 支付场景中，这份定位意味着：

- `PaymentIntent` 需要先规范化，再参与签名绑定
- 风险策略应在 Gateway 层执行，而不是在 Agent 层口头判断
- 高风险转账应由 HumanLink 输出与交易参数绑定的 Assertion
- 审计结果应覆盖 SDK、Gateway 和链上执行三层

---

## 总结

`HumanLink` 的合理技术栈定位不是“做一块更强的指纹板”，而是：

- 用模块化硬件承载可信授权执行
- 用协议定义统一 Assertion 语义
- 用开放验证和审计接口支撑跨平台接入

一句话总结：

**HumanLink 的核心价值是，把 AI 高风险操作的人类授权，从“软件确认”升级为“可验证、可审计、可扩展的授权证明协议”。**
