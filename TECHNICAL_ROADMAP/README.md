## 一、项目概述

### 定位

HumanLink 是 **AI Agent 时代的人类在场授权基础设施**。它不重在构建封闭硬件安全系统，而是设计**开放协议层**，定义面向 AI 高风险操作的**人类在场授权证明**。

类比：MCP 定义了 Agent 如何调用工具，HumanLink 定义了 Agent 执行高风险操作前如何留下不可伪造的人类授权记录。

### 核心设计原则

- **协议优先，硬件作为可信执行载体**：协议层定义 `Challenge`、`actionHash`、`HumanPresenceAssertion`、设备身份、签名格式、验证流程和审计接口；硬件负责执行人类在场验证、保护不可导出私钥，并对与具体操作绑定的授权上下文签名
- **开放接入，基于分立式硬件架构的 HAI 抽象接口**：当前 ESP32 + JM-101 + ATECC608A 是参考实现；HAI 不绑定特定硬件型号，重在定义合规 Issuer 的能力要求和输出格式
- **安全原则参考封闭硬件系统，工程路线不依赖封闭生态**：参考硬件根信任、私钥不可导出、可信确认和防重放等关键安全机制，但不复刻封闭生态

<br />

**HumanLink 是一种基于「分立式认证器 + Secure Element」的开放人类在场授权协议：它借鉴硬件钱包的本地确认与硬件签名架构，将生物/活体检测结果、设备身份、Challenge 和 AI 高风险动作的 actionHash 绑定，并签发可第三方验签的 HumanPresenceAssertion。**

### 竞品空白

HumanLink 填补的空白：**此刻物理在场 + 操作绑定 + 密码学可举证 + 链上可审计 + 开放协议**。

| 竞品方向                | 代表                    | 它解决的            | 它解决不了的               |
| ------------------- | --------------------- | --------------- | -------------------- |
| Agent 支付协议          | Visa TAP, Stripe ACP  | Agent 有没有**权限** | 执行时有没有**人类物理在场**     |
| 软件 HITL 工具          | Permit.io, Auth0 CIBA | 有没有**软件层确认**    | 确认的是不是**真人**，证据能不能举证 |
| Proof of Personhood | Worldcoin             | **注册时**是人       | **此刻执行时**在不在场        |
| 设备生物认证              | Apple Touch ID        | 是不是**设备主人**     | 跨平台操作绑定、链上可审计        |

### Cobo Agentic Wallet vs HumanLink

HumanLink 与 Cobo 解决不同层面的问题：Cobo 是 Agent 钱包执行基础设施，HumanLink 是人类在场授权证明协议层。

| 维度    | Cobo Agentic Wallet                            | HumanLink                                                      |
| ----- | ---------------------------------------------- | -------------------------------------------------------------- |
| 核心定位  | Agent 钱包执行基础设施                                 | 人类在场授权证明协议层                                                    |
| 授权模型  | Pact：owner 批准任务级边界（intent、plan、budget）         | Challenge + actionHash：单次操作级断言                                 |
| 人工确认  | Owner 在 Cobo app 中批准 Pact                      | 用户在 HumanLink 设备上物理确认 actionHash                               |
| 签名私钥  | MPC key shares（资产控制权）                          | SE 独立私钥（授权证明权）                                                 |
| 签名对象  | 链上交易 / 钱包操作；Pact 内容独立可验签签名未明确                  | actionHash / Challenge / 授权上下文                                 |
| 第三方验签 | 依赖 Cobo 钱包体系与平台审计语义；审批日志在 Cobo 平台内部，无法脱离平台独立核验 | 基于 assertion + 设备身份 + registry + revocation 独立验签；审计记录可脱离平台独立核验 |

## 二、HumanLink 协议设计（通用基础设施）

### 四层架构

```
╔═══════════════════════════════════════════════════════════════╗
║                 HumanLink Protocol                           ║
║                                                              ║
║  ┌─ 接入层（本地/云端，同一套 SDK）─────────────────────────┐ ║
║  │  · 生成 Challenge（含 requiredIssuerDID）                 │ ║
║  │  · 10 步验证 Assertion → 可举证授权记录                   │ ║
║  │  · chain_check 配置决定链上步骤是否执行                    │ ║
║  │  · Agent 无权发起或绕过认证                               │ ║
║  └──────────────────────────────────────────────────────────┘ ║
║                            │                                  ║
║  ┌─ 协议核心层 ─────────────┴───────────────────────────────┐ ║
║  │  · Assertion 数据格式规范                                 │ ║
║  │  · Challenge 绑定（action + origin + nonce + requiredDID）│ ║
║  │  · actionHash 含设备公钥，防设备替换攻击                    │ ║
║  │  · 单签名结构（hardwareProof）                            │ ║
║  │  · 设备信任分级（attestation）                            │ ║
║  └──────────────────────────────────────────────────────────┘ ║
║                            │                                  ║
║  ┌─ 身份与链上层 ───────────┴───────────────────────────────┐ ║
║  │  · Device DID (did:key) — 链上 IssuerRegistry 注册        │ ║
║  │  · UserDeviceRegistry — 用户账号 ↔ 设备 DID 绑定          │ ║
║  │  · AssertionStatusRegistry — 断言撤销                     │ ║
║  │  · AuditLog — 高危操作审计摘要（可选）                    │ ║
║  └──────────────────────────────────────────────────────────┘ ║
║                            │                                  ║
║  ┌─ 硬件抽象接口 (HAI) ───┴─────────────────────────────────┐ ║
║  │  · get_device_did() → str                                 │ ║
║  │  · get_attestation() → dict   → 硬件资质证明               │ ║
║  │  · authenticate(h_doc, required_did) → AuthResult         │ ║
║  │  不规定具体硬件，只规定能力要求和输出格式                    │ ║
║  └──────────────────────────────────────────────────────────┘ ║
╚═══════════════════════════════════════════════════════════════╝
```

### 关键流程

**授权流程（10 步验证）**：

1. 结构校验 — type、必选字段完整
2. 设备身份校验 — device.id 与 requiredIssuerDID 匹配
3. Challenge 校验 — actionHash 一致、nonce 未使用、未过期
4. origin 校验 — 来自预期的发起方
5. display 校验 — 用户看到的操作与签名绑定一致
6. 指纹匹配校验 — score ≥ min\_match\_score
7. 传感器校验 — sensorSerial 与设备绑定一致
8. 设备信任校验 — attestation 级别满足 trustPolicy
9. ECDSA 签名校验 — hardwareProof 验签通过
10. 链上校验（可选）— IssuerRegistry.isValidIssuer() + 未撤销

**初始化流程**：设备注册链上 IssuerRegistry → 用户绑定设备 DID → 注册指纹模板

**纠纷举证**：链上核验设备注册状态 + 签名有效性 + 操作绑定关系 → 证明「有已注册用户在该时刻物理在场并确认了此操作」

### 两种接入路径

| <br />   | 本地集成                | 云端集成                                |
| -------- | ------------------- | ----------------------------------- |
| **场景**   | 个人 Agent 助手、消费者应用   | Copilot/Cursor 类平台、企业私有 Agent       |
| **接入方式** | SDK + AI Gateway 直连 | SDK 守护进程 + WebSocket 接收云端 Challenge |
| **设备注册** | 用户自主注册，绑定至个人账号      | 平台管理员注册，绑定至用户账号                     |
| **举证主体** | 用户本人可举证             | 平台可代用户举证                            |
| **付费模式** | 硬件设备 + 增值服务订阅       | SDK 按验证次数收费                         |

## 三、技术栈定位与原则

> 详见 [项目技术栈定位\_原则与优化方向.md](./项目技术栈定位_原则与优化方向.md)

### 三大原则

1. **协议优先，硬件作为可信执行载体**：重在构建面向 AI Agent 高风险操作的开放式人类在场授权协议，而非单一硬件产品
2. **开放接入，基于分立式硬件架构的 HAI 抽象接口**：传感器、MCU、SE 拆分为可替换模块；HAI 不绑定特定硬件，定义能力要求而非型号；不同接入方通过统一 SDK 调用授权层
3. **安全原则参考封闭硬件系统，工程路线不依赖封闭生态**：参考硬件根信任（外设、链路、固件、签名可信）、私钥不可导出、可信确认、上下文绑定签名和防重放等机制

### 硬件架构优化方向

| 方向             | 当前基础                                                   | 待增强点                                                       |
| -------------- | ------------------------------------------------------ | ---------------------------------------------------------- |
| **ESP32 自身可信** | ESP32 接收 H\_doc、调度 JM-101 和 ATECC608A                  | Secure Boot、Flash Encryption、Anti-rollback，防恶意固件绕过指纹直接触发签名 |
| **外设模块可信**     | JM-101 指纹采集与本地模板匹配，返回 matched\_id、score                | 模块级公私钥、模块证书、强 attestation，防认证外设模块替换                        |
| **模块链路可信**     | JM-101↔ESP32 UART、ESP32↔ATECC608A I2C、主机↔设备 USB Serial | nonce、counter、MAC 或加密通道，保护 Challenge 哈希和认证结果               |
| **授权证据与审计可信**  | Assertion 结构 + ECDSA 签名 + H\_doc/H\_final 中间哈希         | 纳入模块证书、活体结果签名、ESP32 固件状态、设备端确认状态                           |
| **用户确认可信**     | display 由验证方填写，用户看到操作摘要                                | 设备端可信显示、按钮确认、短 hash 校验                                     |
| **活体能力可信**     | JM-101 指纹匹配，对伪造攻击抵抗不足                                  | 升级为具备本地活体判断、防伪造、模块证书和签名输出的生物认证模组                           |

## 四、生物认证授权技术分析

> 详见 [生物认证授权技术分析.md](./生物认证授权技术分析.md)

### 技术构成

1. **生物认证编排层**：统一管理认证请求、系统 UI、流程和模态选择；协调底层 TEE、Keystore、StrongBox 等安全模块
2. **安全元件 (SE)**：保护密钥、证书和设备身份；芯片内部完成安全存储密钥、执行签名/解密、设备认证、抗物理篡改
3. **可信执行环境 (TEE)**：主处理器中的隔离执行环境；保护敏感数据和关键判定逻辑，核心是「在受保护边界内执行」而非存储
4. **安全日志审计层**：对认证、授权、密钥使用事件进行记录、存储与审查的系统级证据层

### 四大技术路线对比

生物认证授权技术路线的分类应基于技术问题而非厂商：**可信边界在哪、谁负责编排、私钥在哪、输出什么、授权对象是什么、开放性如何**。按此维度分为四类路线：

| 维度             | 分立式认证器 + SE 架构 (HumanLink参考)                      | 一体化安全域架构                                | 平台编排型 TEE / StrongBox 架构                              | 硬件认证器 / 设备认证架构                            |
| -------------- | ------------------------------------------------- | --------------------------------------- | ----------------------------------------------------- | ----------------------------------------- |
| **典型形态**       | 生物模块 + MCU + SE + SDK + Assertion                 | 传感器 + SoC + Secure Enclave / 安全子系统 + OS | BiometricPrompt / 系统认证框架 + TEE/Keystore/StrongBox/eSE | YubiKey、FIDO2 security key、PIV smart card |
| **可信边界**       | 传感器、MCU、SE 分离，需 secure boot + 链路保护 + SE 签名补强      | 单一强安全域，模板/匹配/密钥尽量在同一安全域                 | OS + TEE/StrongBox/eSE，取决于 OEM 实现                     | 独立认证器边界，主机通常不持有私钥                         |
| **编排主体**       | MCU 负责 Challenge 处理、模块调度、结果组装                     | SoC / 系统安全子系统统一编排                       | 系统认证框架（BiometricPrompt）统一编排                           | Client/RP 与 Authenticator 按协议交互           |
| **私钥保护**       | 独立 Secure Element（ATECC608A）                      | Secure Enclave / 硬件安全域                  | TEE/StrongBox/Keystore/eSE                            | 认证器内部安全芯片                                 |
| **授权输出**       | 可设计为 HumanPresenceAssertion，绑定操作、设备、Challenge 与签名 | 本机认证结果或系统授权结果                           | 系统认证状态、Keystore/StrongBox 授权结果                        | WebAuthn assertion、设备签名、证书                |
| **操作绑定能力**     | 强：绑定 actionHash + Challenge + 设备 DID + 模块状态       | 中等：支付确认较强，不开放为通用操作断言                    | 弱到中等：主要绑定系统认证请求或密钥使用请求                                | 中等：可绑定 challenge，默认语义为登录认证                |
| **第三方验证与举证**   | 强：可独立验签、查设备状态、查撤销状态、生成审计证据                        | 弱，主要依赖本机系统或封闭生态                         | 弱到中等，依赖平台 API、OEM 安全实现和系统日志                           | 中到强，RP 可验证签名，但不一定表达具体人类授权                 |
| **开放性**        | 高：可替换传感器/MCU/SE，接入不同 Agent/Gateway/企业平台           | 低：强绑定硬件和系统生态                            | 中等：生态内兼容较强，但 OEM 差异大                                  | 高：FIDO/WebAuthn 标准成熟，跨平台部署广               |
| **Agent 场景适配** | 强：拦截高风险 Agent 行为并生成授权证明                           | 弱：不是为 Agent 授权设计                        | 弱到中等：可辅助登录，难绑定具体 Agent action                         | 中等：可做强认证，不天然表达 Agent actionHash 授权        |
| **主要优势**       | 开放、可组合、可审计、适合 AI 高风险动作授权                          | 安全边界强、体验好、系统协同能力强                       | 接口统一、生态覆盖广、适合移动端大规模部署                                 | 标准成熟、抗钓鱼、硬件私钥保护成熟                         |
| **主要短板**       | 工程复杂，需补强模块可信、链路安全和固件可信                            | 封闭，难形成开放授权协议                            | OEM 差异大，外部证明能力弱                                       | 主要强在认证，不完整表达「人类对具体操作授权」                   |

**HumanLink 选用分立式认证器 + SE 路线的核心原因**：开放性强、成本低、可移植性高，更适合扩展为跨平台人类授权协议层。代价是安全边界分散，需在 Secure Boot、模块 attestation、链路保护上持续补强。

## 五、当前状态与路线

### 当前阶段（黑客松 Demo）

- ESP32 + JM-101 + ATECC608A 参考实现已跑通
- SDK 本地验证、设备通信、审计记录已实现
- HumanLinkPay 支付场景 Demo 已集成
- 指纹授权诚实标注为 JM-101 指纹匹配（非强活体检测）
- 不包含：ESP32 Secure Boot、模块证书/attestation、链路加密、强活体检测

### 短期增强方向

- ESP32 Secure Boot + Flash Encryption + Anti-rollback
- 模块证书与 attestation
- 链路通信保护（nonce / MAC）
- 设备端可信显示

### 中长期方向

- 强活体检测模组升级
- HAI 接口标准化与多 OEM Issuer 生态
- TEE / Chainlink Functions 辅助验证
- 企业级合规方案（SDK + 审计面板 + 参考硬件打包）
